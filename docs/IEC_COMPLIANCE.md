# IEC 61131-3 Compliance

STruC++ implements the Structured Text (ST) language from IEC 61131-3. This document lists supported features and known gaps. The compiler also supports common CODESYS extensions where noted.

| TIME | Supported | 32-bit unsigned milliseconds, as on the PLC (4 bytes, `SIZEOF(TIME)` is 4): T#0ms to T#49d17h2m47s295ms, and arithmetic wraps modulo 2^32 ms (`T#1s - T#2s` is T#49d17h2m46s296ms). A negative TIME literal, one with a part below a millisecond (`T#1us`; an LTIME holds those) or one past the range is an error, in sources and test files. So is the negation of a TIME literal, a TIME constant (also of a type derived from TIME) or a constant expression of them whose value is above 0 (`-T#5s`, `-C`, `-(T#5s - T#1s)`), in a statement and in every initial value (a STRUCT field default, a structure, array or FB instance initialiser); `-T#0s` and `-C0` of a constant of 0 are accepted, and `-t` of a TIME variable wraps. A TIME times or divided by a number gives a TIME: an integer exactly, a REAL computed in double and truncated toward zero (`T#49ms / 49.0` is T#1ms); `t MOD n` and `t MOD T#300ms` are unsigned (MOD 0 gives 0); `t1 / t2` is the integer quotient of the two millisecond counts, as a TIME; `t1 * t2` of two of them (an LTIME with a TIME included) and `t ** n` are errors, also when an operand is a dereference or a SEL, MUX, LIMIT, MAX or MIN result. A TIME with an LTIME in `/` or MOD widens to an LTIME, as in `+` and `-` (`T#7s / LTIME#3s` is the LTIME quotient 2, `T#7s MOD LTIME#3s` is LTIME#1s). Date and time arithmetic follows Table 30, in every mode: TIME + or - TIME, a DATE, TOD or DT + or - a TIME (also TIME + one), and DT - DT, TOD - TOD or DATE - DATE (a TIME), an L form counting as its short one; anything else with a DATE, TOD or DT operand is an error (`DT + DT`, `TOD + TOD`, `TIME - DT`, `DT - TOD`, `DT * 2`, `DATE / 2`, `DT / DT`, `DATE MOD DATE`, `LDT + LDT`), except a TOD or DT MOD a TIME (below). A TIME, DATE, TOD or DT + or - a number (`t + 100`, `n + t`, `d + 1`) is an error in every mode too; a number times a TIME is a TIME in either order (`T#5s - n * T#1s`). An LTIME, LDATE, LTOD or LDT + or - a number (in ns, or days for LDATE) and a TOD or DT MOD a number are accepted, and refused under `--dialect iec-3` and `--strict`. A TOD or DT MOD a TIME is the time within that period, of the TOD or DT type (`TOD#01:00:00.500 MOD T#1h` is TOD#00:00:00.500; a DT, in seconds, is taken in ms and the remainder truncated to whole seconds, `DT MOD T#1500ms` gives 0 or 1 s); MOD a TIME of 0 gives 0. Every other `/` or MOD between two date and time types of different kinds, or of a number by one, is an error (`Operator 'MOD' does not apply to DATE and TIME`, also `TOD / TIME`, `TIME MOD DATE`, `DINT / TIME`; a DATE MOD a TIME is refused because the remainder is no date), and so is a date or time as the second argument of `DIV_TIME` (except a value of the first argument's type) or `MUL_TIME`. An LTIME stored in a TIME or a type derived from it (an assignment, an FB, FUNCTION or METHOD input, a STRUCT initialiser field) is truncated to ms and wrapped; as the declared initial value of a TIME variable, a type derived from TIME or a TIME STRUCT field it is an error (`Cannot assign LTIME to TIME`). `TIME()` gives the scan clock in ms and wraps after 49.7 days; TON, TOF and TP measure `TIME() - start`, so they stay right across the wrap. `STRING_TO_TIME` of a negative text wraps, of digits below a millisecond truncates |
| DATE | Supported | 32-bit unsigned seconds since 1970-01-01, a whole number of days counted from 1970 and wrapped (4 bytes): D#1970-01-01 to D#2106-02-07, a literal outside it is an error (`D#1969-12-31`: a 32-bit DATE cannot hold a date before 1970, use LDATE). A day before 1970 reached at run time wraps modulo 2^32 seconds, as the PLC's unsigned arithmetic does, and every route gives the same value: `CONCAT_DATE(1969, 12, 31)`, `D#1970-01-01 - T#1d`, `STRING_TO_DATE('1969-12-31')`, `LDATE_TO_DATE(LDATE#1969-12-31)` and `LINT_TO_DATE(-86400)` are all 4294880896 (-86400 s), and adding `T#1d` to it gives D#1970-01-01; a DATE moves by whole days in its raw seconds. A wrapped pre-1970 DATE is not on a day boundary of the unsigned count: 4294880896 s is 2106-02-06-06:28:16, so it compares unequal to `D#2106-02-06`, and `DATE_TO_DT` or `DATE_TO_UDINT` of it give that instant, not the midnight of the 2106 day it splits and prints as. `DT_TO_DATE` keeps the PLC's `DT - DT MOD 86400` of the wrapped seconds, so a DT before 1970 gives a different DATE value (`DT_TO_DATE(DWORD_TO_DT(-1))` is 63104 s after `DINT_TO_DATE(-1)`). An integer from 0 up converts modulo 2^32 and then down to its day, as before (`LINT_TO_DATE(4294967296)` is D#1970-01-01); one below 0 goes down to its day and then wraps. DATE - DATE is a TIME (Table 35; `D#2024-01-20 - D#2024-01-15` is T#5d), and a DATE or LDATE plus or minus a TIME or LTIME is the date of the day that holds the resulting instant, counting from the date's midnight (floor: `D#2024-01-15 - T#36h` is D#2024-01-13, `D#2024-01-15 + T#36h` is D#2024-01-16); the arithmetic is done in days, so it holds for any date, not only those within 292 years of 1970. Operands of a type derived from DATE or TIME, a REFERENCE TO or dereference of one, the result of a call or FB output, or a SEL, MUX, LIMIT, MAX or MIN of them follow the same rules, in a statement, an initial value, an array initialiser and a STRUCT field default. `DT_TO_DATE` and `DT_TO_TOD` (and their DATE_AND_TIME spellings and the overloaded `TO_DATE`/`TO_TOD` of a DT, a type derived from DT or a `CONCAT_DATE_TOD` result) take only the date or the time of day (Table 26). Before this change they copied the date-and-time's nanosecond count and DATE - DATE gave a day count, which changed the results of OSCAT's DCF77, SUN_POS, CALENDAR_CALC, DST, DT_TO_SDT, DT_TO_STRF and their callers RTC_2, LTIME_TO_UTC and UTC_TO_LTIME |
| TIME_OF_DAY | Supported | 32-bit unsigned milliseconds since midnight (4 bytes): TOD#00:00:00 to TOD#23:59:59.999, a literal past it is an error. A literal digit below a millisecond (`TOD#12:00:00.1234`) is dropped with a warning, and is an error under `--dialect iec-3` and `--strict`; the same holds for a fraction of a second in a DT literal (`DT#2020-01-01-00:00:00.5`) and a digit below a nanosecond in an LTOD or LDT literal. TOD + TIME wraps modulo 2^32 ms, as on the PLC, not modulo 24 hours; TOD - TOD is a TIME, a variable or a typed literal on either side |
| DATE_AND_TIME | Supported | 32-bit unsigned seconds since 1970-01-01-00:00:00 (4 bytes): DT#1970-01-01-00:00:00 to DT#2106-02-07-06:28:15, a literal outside it is an error (one before 1970: use LDT); a run-time value before 1970 wraps modulo 2^32 seconds, the same on every route (`CONCAT_DT(1969, 12, 31, 23, 59, 58, 0)`, `DT#1970-01-01-00:00:00 - T#2s` and `LDT_TO_DT(LDT#1969-12-31-23:59:58)` are 4294967294). A fraction of a second in a DT literal is dropped (see the TIME_OF_DAY row). DT +/- TIME is the second that holds the resulting instant; DT - DT is a TIME, a variable or a typed literal on either side |
| LTIME | Supported | Ed. 3 elementary type (Table 10): a signed 64-bit duration in nanoseconds (8 bytes), in every dialect. Literals `LTIME#` and `LT#` take every unit (d, h, m, s, ms, us, ns), a sign, a fraction and underscores (Table 8); one outside the 64-bit range is an error. TIME converts to LTIME implicitly and LTIME to TIME only explicitly (Figures 11 and 12); TIME and LTIME operands mix to an LTIME result. Conversions `TIME_TO_LTIME`, `LTIME_TO_TIME`, `TO_LTIME`, `LTIME_TO_<integer>` and `<integer>_TO_LTIME` (the integer counts nanoseconds), and the arithmetic functions `ADD_LTIME`, `SUB_LTIME`, `MUL_LTIME`, `DIV_LTIME`. A TIME widens to an LTIME exactly; `LTIME_TO_TIME` truncates to milliseconds and wraps modulo 2^32. `LTIME()` gives the scan clock as an LTIME (no wrap), and LTON, LTOF and LTP run on it. The debugger reads an LTIME leaf under its own tag (8 bytes, `duration-ns-i64` in `libs/iec-types.json`) |
| LDATE, LTOD (LTIME_OF_DAY), LDT (LDATE_AND_TIME) | Supported | Ed. 3 elementary types (Table 10), in every dialect, 8 bytes: LTOD and LDT as signed nanoseconds. Table 10 specifies LDATE as signed 64-bit nanoseconds since 1970-01-01; it is stored as days since then instead, an implementation choice that changes no result a program computes (conversions to and from integers count nanoseconds). Literals `LDATE#`/`LD#`, `LTOD#`/`LTIME_OF_DAY#` and `LDT#`/`LDATE_AND_TIME#` take the forms of the short ones (Table 9). DATE, TOD and DT convert implicitly to their long form, exactly, not back; a long value converted to the short form is truncated to its unit (s or ms) and wraps modulo 2^32 (Figures 11 and 12). The difference of two long instants of one kind (a short one converting) is an LTIME, and a long instant plus or minus a TIME or LTIME keeps its type; an LDATE plus or minus a duration is the date of the day that holds the resulting instant (see the DATE row). Conversions between the long and short forms and to and from integers (in nanoseconds, LDATE included), `LDT_TO_LDATE` / `LDT_TO_LTOD` (the date or time of day of the instant, Table 26) and `LDATE_TO_LDT` (its midnight). A user TYPE already named like one of these types stays the user's type. The CONCAT_ and SPLIT_ functions for them are those of Table 36 |
| STRING | Supported | Parameterized length: STRING(N), or STRING[N] as Ed. 3 writes it (the same type, in every dialect), default 254 (80 under the feature `string_default_80`, see [DIALECTS.md](DIALECTS.md#default-string-length)). A STRING or WSTRING literal longer than the variable, input, STRUCT field or FUNCTION or METHOD result it is stored in (an alias of STRING(n), an element of an ARRAY or STRUCT initialiser included) is cut to its length, with one warning in every mode (`A STRING literal of 6 characters is longer than STRING(3): it is cut to 3`); a WSTRING's length is counted in UTF-16 code units, as it is stored (`A WSTRING literal of 2 UTF-16 code units is longer than WSTRING(1)`). N is an unsigned integer, underscores allowed (`STRING[1_0]` is 10; under `--dialect iec-3` and `--strict` only between two digits, so `STRING[1__0]` is an error); in parentheses it may also be based (`STRING(16#20)` is 32), in brackets not. N may be a constant: a VAR_GLOBAL CONSTANT, a POU's VAR CONSTANT or an expression of them takes its value, a caller-supplied constant (`-D`) keeps its name. An element of an ARRAY OF STRING(N) or ARRAY OF REF_TO STRING(N), inline, named, a STRUCT field or an ARRAY[*] parameter, has that length: a longer value is truncated to N. Arrays whose elements differ only in that length assign and pass element by element (an in/out by copy-in / copy-out). Typed literals `STRING#'abc'` and `WSTRING#"abc"` (Table 6) are that type and take no adaptation to CHAR or WSTRING; the other quotes (`STRING#"abc"`, `WSTRING#'abc'`, `CHAR#"a"`) are an error. A STRING holds Windows-1252 characters, one byte each, which matches the behaviour of common vendor toolchains: `LEN('ä')` is 1 and STRING(N) holds N such characters. A character Windows-1252 lacks in a STRING literal is an error at its position (`Character '☃' (U+2603) cannot be stored in a STRING, which holds Windows-1252 characters; use a WSTRING literal ("...") for it`). See RUNTIME.md for the debugger and REPL |
| WSTRING | Supported | Parameterized length: WSTRING(N) or WSTRING[N]. STRING_TO_WSTRING widens each STRING character to its Windows-1252 code point; WSTRING_TO_STRING writes a character Windows-1252 lacks as `?` |
| CHAR, WCHAR | Supported | Ed. 3 elementary types (Table 10), in every dialect: a CHAR is one Windows-1252 byte, a WCHAR one UTF-16 code unit. Literals `CHAR#'A'`, `WCHAR#"A"` and `WCHAR#'A'` (Table 6, with `$` escapes) hold exactly one character, a CHAR literal one Windows-1252 has; `CHAR#16#41` and `WCHAR#8364` give the code (Table 5). A one-character `'A'` where a CHAR is expected, or `"A"` where a WCHAR is (Table 6 1b, 2b), is that character: in an assignment or initial value (an alias of CHAR, an array element and a STRUCT field included), as a function, method or function block input (positional or named, in every call form: an instance, an array element, a STRUCT member, a dereference, a REFERENCE TO, THIS, SUPER, an interface or a bare method), as the source of a `CHAR_TO_...` or `WCHAR_TO_...` conversion, beside a CHAR in a comparison (a CHAR reached through `^`, `p^ = 'b'`, `pa^[i] := 'b'`, `CASE p^ OF 'a':`, included; a WCHAR stored into one is refused), as an argument of MAX/MIN/LIMIT/GT/.../SEL/MUX among CHARs or where their result is a CHAR, and as a CASE label. Any other value there (a longer literal, a number, a WCHAR for a CHAR) is refused, as its assignment is. SEL, MUX, LIMIT, MAX and MIN of CHARs are a CHAR. A CASE range `'a'..'c'` selects every code in it. `s[i]` reads or writes the i-th character of a STRING (a CHAR) or WSTRING (a WCHAR), from 1 to the string's current length; outside it is the run-time out-of-bounds error arrays raise. `s[i]` is no variable: binding it to a VAR_IN_OUT or taking its REF() is an error (assign it to a CHAR first). CHAR and WCHAR compare only with their own type, by code (`<`, MAX, MIN, LIMIT, GT and the others, through aliases), take no arithmetic or logic, and are CASE selectors. Explicit conversions `CHAR_TO_<bit string or integer>` (the Windows-1252 code) and back, `WCHAR_TO_<...>` (the code unit) and back, `CHAR_TO_STRING`, `WCHAR_TO_WSTRING`, `CHAR_TO_WCHAR`, `WCHAR_TO_CHAR`, `CHAR_TO_WSTRING`, `WCHAR_TO_STRING`, `STRING_TO_WCHAR` and `WSTRING_TO_CHAR` (a STRING or WSTRING, a literal included, gives its first character; across the widths through Windows-1252, a WCHAR it lacks becoming `?`). EN/ENO on MAX, MIN, LIMIT, the comparisons, SEL and MUX over CHAR or WCHAR runs the call only when EN is TRUE and writes ENO, also where the call is nested in an expression (not in a `--test` file, where a nested call with EN/ENO is refused like any other). The debugger reads a CHAR leaf as a BYTE and a WCHAR leaf as a WORD |

| TYPE ... END_TYPE | Supported | Type aliases. Call it with or without arguments (`s.tmr(IN := x)`, `s.tmr();`). A STRUCT inheriting another's fields (`TYPE ST_B EXTENDS ST_A : STRUCT`) is an extension (IEC 61131-3 `Struct_Type_Decl` takes no EXTENDS): the feature `struct_extends` (refused with no dialect flag and under `--dialect iec-3`). | STRUCT OVERLAP | Partial | The Ed. 3 overlay form (Table 11), in every dialect, in its form without locations: `TYPE T : STRUCT OVERLAP a : DINT; b : ARRAY[0..3] OF BYTE; END_STRUCT END_TYPE` is compiled as the UNION of the same members (host byte order), with the UNION row's rules for members. As Ed. 3 requires for an overlapped structure, a variable or member of it takes no explicit initial value, and its members none either. Not supported: members at relative locations (`head AT %B0 : INT;`), which are a parse error. A field named `overlap`, or a first member named by a keyword allowed as a field name (`STRUCT OVERLAP ON : BOOL; ...`), parses as a field |
| Enumerations | Supported | With optional base type before the value list, `DINT (A, B)`. The base written after the list, `(A, B) DINT`, is a vendor ordering: the feature `postfix_enum_base` (refused with no dialect flag and under `--dialect iec-3`), same meaning and C++ as the base-first form. A type default (`(A, B) := B`, `:= E#B` or `:= E.B`) must be one of the type's own values. A value (`E#M`, `E.M` or a bare member) has its enumeration's type. `E.M` is a vendor spelling of `E#M` (Ed. 3 qualifies with `#`): the feature `enum_dot_qualify` (in the default set, refused under `--dialect iec-3` with a hint naming `E#M`). The initial value of an enumeration variable, STRUCT field or array element, also inside an array literal or a structure initializer, must be a value of that enumeration (`Cannot assign E3 to E2`, `'Z' is not a value of enumeration E2`), and an enumeration is not used as a number without a conversion such as `TO_INT`. An alias of an enumeration (`TYPE E2A : E2;`, also chained) is that enumeration: its variables take the enumeration's values and variables, and are declared with the same C++ wrapper. An enumeration value is not an integer: as an array index, bound to an integer input or to an input of another enumeration, or as a CASE label of another type than the selector, it is an error (an alias of the enumeration is that enumeration). `E#M` names the type E even where a variable is named E. SEL and MUX of values of one enumeration (variables, literals and aliases mixed) yield that enumeration; an input of another type next to them is an error |
| Initialized type declarations | Supported | A type may carry its own default (`Setpoint : REAL := 25.0;`, `Origin : Point := (x := 0.0);`), inherited by every declaration of the type that has no initializer |
| ARRAY (1D) | Supported | Arbitrary bounds: ARRAY[1..10] OF INT. A bound is an integer constant expression, in a named array type and inline alike: literals, constants (a POU's `VAR CONSTANT`, a `VAR_GLOBAL CONSTANT` of any file, also list-qualified, a `-D` constant) and `+ - * / MOD` on them. An enumeration value is also accepted as a bound and counts as its number (`ARRAY[E#A..E#C]`), a vendor extension accepted in every dialect; the element is still indexed by an integer (`a[TO_INT(E#B)]`). A bound that is not a constant is an error (`The bounds of an ARRAY must be integer constants: 'N' is not a constant`). An index outside the bounds is a run-time fault naming the index, the POU, the line and the running task (`Array index out of bounds: 5 in MAIN, line 7, task FAST`); building the C++ with `-DSTRUCPP_NO_BOUNDS_CHECK` leaves the check out, see [RUNTIME.md](RUNTIME.md) |

| ARRAY (3D) | Supported | ARRAY[1..3, 1..4, 1..5] OF INT |
| ARRAY OF function block | Supported | Declaration, member access, and element invocation (`units[i](step := 1.0)`), also of a global array, through its global variable list (`GVL_A.units[i](...)`) and through a member path (`h.arr[i](...)`). A named TYPE of one (`BeltPair : ARRAY[0..1] OF FB_Belt`) may be a member, a STRUCT field, a global, or a method or interface method parameter. A method call on an element (`units[0].M()`) works like any method call through a member chain (see Method call) |
| ARRAY[*] (VLA) | Supported | Variable-length array parameters (Ed. 3 6.5.3): a FUNCTION or METHOD VAR_INPUT, VAR_OUTPUT or VAR_IN_OUT and a FUNCTION_BLOCK VAR_IN_OUT, inline or through a TYPE of an `ARRAY[*]`. Anywhere else an `ARRAY[*]` has no size and is an error in every mode (`'V' is a variable-length ARRAY[*] in a VAR_GLOBAL: it needs fixed bounds there; ...`): a top-level or CONFIGURATION VAR_GLOBAL, a VAR or VAR_TEMP of any POU, a PROGRAM's or FUNCTION_BLOCK's VAR_INPUT or VAR_OUTPUT (an FB input was accepted before as a view of the caller's array), a METHOD's VAR_INST and a STRUCT field (a UNION member has its own message). A POINTER TO ARRAY[*] is a pointer, of fixed size, and stays accepted |
| Subranges | Supported | Runtime validation: a store into a variable of a subrange type (or an alias of one, a STRUCT field or ARRAY element of one included), by assignment, FB or FUNCTION input, output or result, global or CONFIGURATION global, outside the range is a run-time fault naming the variable, the value, the range, the POU, the line and the running task (`Value 42 outside 0..10 stored in S in MAIN, line 10`), see [RUNTIME.md](RUNTIME.md). A subrange variable with no initial value starts at the lower bound; a constant initial value outside the range is an error (`The initial value 42 of 'X' is outside its subrange 0..10`), for a variable, a STRUCT field, an ARRAY element and a TYPE's own default. A FOR control variable of a subrange type is refused |
| REF_TO | Supported | IEC reference type (explicit dereference). `REF(x)` and `r REF= x` of an elementary, STRING, WSTRING, enumeration, STRUCT, ARRAY or function block variable or STRUCT field; `r^.field`, `r^.M()`. `REF()`, `ADR()` and `REF=` of a CONFIGURATION global refer to its storage, outside its lock: the compiler warns that under `STRUCPP_THREADED` accesses through the result are not serialized with other tasks. Not yet: `REF()` of an element of an ARRAY OF an enumeration, and `REF_TO STRING(n)` / `WSTRING(n)` of a length other than the default |
| REFERENCE_TO | Supported | Vendor reference type (implicit dereference); a vendor spelling: the feature `reference_to`, refused under `--dialect iec-3`. A `REFERENCE TO` VAR_INPUT of a function block, function or method is bound to its argument at the call (named or positional), so reads and writes through it reach the argument; an FB input keeps its binding until the next call that passes it. So is one of a library FUNCTION, whose archive records it (`referenceKind` on the parameter); an archive built before that reads the input as a plain value, and the call fails to build until the library is rebuilt. The argument must be a variable (a local, global, member, array element, STRUCT field, `p^` or another `REFERENCE TO`) of the referenced type or an alias of it: an expression, a constant, another type or a subrange variable is an error. A `REFERENCE TO` a STRUCT or function block reaches its members and methods (`rf.a`, `rr.M()`). Reading or writing an unbound `REFERENCE TO` raises the null-reference fault, as a NULL REF_TO dereference does. A `REFERENCE TO STRING` or `WSTRING` reads as the string it is bound to, in string functions, comparisons and assignments. `^` does not apply to a `REFERENCE TO` (it is dereferenced implicitly) and is an error. Not supported yet at compile: binding a `REFERENCE TO` (input or `REF=`) to a variable of an alias type |
| POINTER TO | Supported | Vendor pointer type with dereference via ^; a vendor spelling: the feature `pointer_to`, refused under `--dialect iec-3` |

## Program Organization Units

| POU | Status | Notes |
|-----|--------|-------|
| PROGRAM | Supported | With CONFIGURATION/RESOURCE/TASK structure |
| FUNCTION | Supported | With return type, all parameter modes. EN and ENO (`F(EN := b, x := 1, ENO => ok)`) are supported on a call of a FUNCTION, standard function, library FUNCTION or METHOD written as a statement or as the whole right-hand side of an assignment: with EN FALSE the call is not made, none of its inputs is evaluated, the target keeps its value and ENO is FALSE. On a call anywhere else (inside a larger expression, a condition, an argument of another call, an initial value) they are an error in every mode (`EN/ENO are only supported on a call written as a statement or as the whole right-hand side of an assignment`), except on the standard MAX, MIN, LIMIT, comparisons, SEL and MUX of CHAR or WCHAR (see CHAR, WCHAR) |
| FUNCTION_BLOCK | Supported | Instantiation, invocation, member access. A bare call `f(...)` of an FB instance in scope (a local, a member, or a member inherited from a base FB) or of a PROGRAM invokes it, also when a FUNCTION or standard function has the same name. Every FB and PROGRAM has an implicit ENO output (TRUE after a call, FALSE when EN is FALSE). One that declares ENO itself gets no implicit one: a declared BOOL ENO is the ENO output, set TRUE before the body, which may clear it, and read by `ENO =>`; in a PROGRAM or an FB without a base, a declared ENO of another type is an error. A named argument of an invocation (`fb(a := 1)`, `inst.fb(a := 1)`, `a.b.fb(a := 1)`) that names no input, output or in/out of a function block declared in the compile is an error in every mode, including one naming a VAR, VAR_TEMP or CONSTANT local, a VAR_EXTERNAL, a method, a property or an action. From outside a function block only its interface is reachable (Ed. 3 Figure 13, 6.6.5.10), in every dialect, which matches the behaviour of common vendor toolchains: a VAR_INPUT is written (`f.i := 1`, `f(i := 1)`) but not read, a VAR_OUTPUT is read (`x := f.o`, `f(o => x)`) but not written, a VAR_IN_OUT is bound in the call and not reached through the instance, and VAR, VAR_TEMP and VAR_EXTERNAL members are internal: reading or writing them, an instance initializer naming them (`f : FB := (v := 3)`) and a call through an FB instance held in them (`o.inner(...)`, `o.inner.M()`, `o.inner.x`) are errors, for user and library blocks and in test files (where a test may reach an instance it MOCKs, and the path to it; from the mocked instance down the rule holds). Inside the block, its methods and the blocks derived from it everything stays reachable, also on another instance of the type. EN and ENO are always reachable. A VAR section's access specifier changes the internal rule: `VAR PUBLIC` is reachable from anywhere, `VAR PRIVATE` only inside the declaring block (not from derived blocks, also not through THIS or SUPER), `VAR PROTECTED` is the default; `VAR INTERNAL` is treated as PROTECTED, since namespaces are not supported. A specifier on another section or outside a FUNCTION_BLOCK, or two on one section, is an error. A library archive carries PUBLIC and PRIVATE for its blocks' variables; an older archive's are PROTECTED |
| INTERFACE | Supported | Method prototypes. PROPERTY prototypes (explicit `GET END_GET` / `SET END_SET`) are not in Ed. 3, where an interface holds method prototypes only: a vendor extension, the feature `property` (refused with no dialect flag and under `--dialect iec-3`; see [DIALECTS.md](DIALECTS.md)) |
| ACTION | Supported | ACTION blocks of PROGRAMs and FUNCTION_BLOCKs, written before or after the owner's body (before it, they may be mixed with VAR blocks and methods), called as Name() inside the owner and inst.Name() on an instance; no SFC action qualifiers. Extensions: calling an action directly from ST, and the top-level `ACTION Owner.Name` form; IEC declares actions inside the POU and controls them from SFC steps. An ACTION in ST is the feature `st_actions` (in the default set, refused under `--dialect iec-3`), see [DIALECTS.md](DIALECTS.md). Both forms parse (`ACTION Name[:]` after the body, `ACTION Owner.Name[:]` at top level; `ACTION` is contextual, `END_ACTION` reserved); each action is lowered to a parameterless PUBLIC method of its owner, needs no dialect feature, cannot override or be overridden, and never implements an INTERFACE method. A program's actions can be called only inside the program, or by its name from any POU with the feature `program_methods` |
| Instruction List (IL) bodies | Supported | An IL body of a PROGRAM, FUNCTION or FUNCTION_BLOCK is transpiled to ST. IL is deprecated in Ed. 3 (removed in Ed. 4): under `--dialect iec-3` each IL body gets a warning, see [DIALECTS.md](DIALECTS.md#rules-of-the-iec-3-profile-itself) |

**Names of standard functions are not reserved.** A user FUNCTION named like a standard function or operator
(`MAX`, `LEN`, `ADR`, `SIZEOF`, `INT_TO_REAL`) is the function a call of that name reaches, with its own
parameters. A library FUNCTION named like a standard function (OSCAT's `ROUND(IN, N)`, `ATAN2`) is reached
by a call whose arguments, positional or named, fit only its own signature (`ROUND(x, 2)`,
`ROUND(N := 3, IN := x)`); a call the standard function takes keeps the standard function (`ROUND(x)`),
whatever order the libraries are loaded in. A FUNCTION, FUNCTION_BLOCK, INTERFACE or TYPE named like a function the C++ runtime declares
(`SUB`, `MID`, `LIMIT`, `TRUNC_INT`) is emitted as `NAME_` in the generated C++; diagnostics, the debug table
and the REPL keep the ST name. So is a variable, STRUCT field or local named like a user type, whatever its
case, that another declaration of the same PROGRAM, FUNCTION_BLOCK (with its methods), FUNCTION or STRUCT
uses (`s3 : STRING(3)` next to `a : S3`): the name would otherwise hide the type in the C++ class or body.
A FUNCTION or METHOD parameter keeps its name. A FUNCTION or standard function called where a variable of its name, in any case, is in scope (a local, a parameter or a member that is no FB instance) is reached through its namespace in the C++; an FB instance of that name is what the call invokes, and its call has no value. Likewise a global read or written inside a FUNCTION_BLOCK or PROGRAM (its body, methods, actions or property accessors) that has a method or action of the global's name, its own, inherited or from an implemented interface, is reached through its namespace; inside that method its name still means the method's result, and a call `NAME(...)` in that class, as a statement or in an expression, calls the method, not a global instance of that name.

**Implicit conversions** (Figures 11 and 12) are accepted in every dialect and under `--strict`: an integer
into a wider one of the same signedness, an unsigned integer into a wider signed one (USINT into INT, DINT or
LINT; UINT into DINT or LINT; UDINT into LINT), SINT, INT, USINT and UINT into REAL, an integer up to 32 bits into
LREAL, REAL into LREAL, a bit string into a wider one (BOOL into BYTE included), and TIME, DT, DATE and TOD into
their long forms. Without `--strict` some conversions the figures leave explicit are also accepted (a bit string
and an integer of a sufficient width, DINT into REAL), and a narrowing is a warning; `--strict` refuses every
conversion the figures do not list, a bit string to or from an integer or REAL included.

**REAL/LREAL to integer.** `REAL_TO_*` and `LREAL_TO_*` to an integer type round to nearest (half away from
zero), saturate at the target's range and give 0 for NaN, instead of the undefined behaviour of a plain C++
cast. `*_TO_BOOL` still rounds first (0.4 is FALSE). `TRUNC` returns an integer, as the standard says: DINT for
REAL and LINT for LREAL (truncating toward zero, saturating). Under `--strict` an assignment of `TRUNC(r)` to an
INT needs `DINT_TO_INT`; without it the narrowing is accepted, as library code expects. The extension
feature `trunc_dint` (off by default and under `iec-3`) makes `TRUNC` of an LREAL a DINT as well (saturating
at the DINT range); see [DIALECTS.md](DIALECTS.md). Ed. 3 deprecates the untyped `TRUNC`: under `--dialect iec-3`
each call gets a warning that names the typed form, see [DIALECTS.md](DIALECTS.md#rules-of-the-iec-3-profile-itself).

**Typed truncation** (IEC 61131-3 Ed. 3, Table 22) is supported in every dialect for every ANY_REAL x ANY_INT
pair: `TRUNC_<int>` (e.g. `TRUNC_INT`) takes a REAL or an LREAL, `REAL_TRUNC_<int>` and `LREAL_TRUNC_<int>`
(e.g. `REAL_TRUNC_SINT`, `LREAL_TRUNC_ULINT`) take that type; `<int>` is SINT, INT, DINT, LINT, USINT, UINT,
UDINT or ULINT and is the result type. They truncate toward zero (`TRUNC_INT(-2.7)` is -2), saturate at the
target's range (`TRUNC_SINT(1000.0)` is 127, `TRUNC_UINT(-1.5)` is 0) and give 0 for NaN, as `TRUNC` does. An
LREAL argument to a `REAL_TRUNC_*` is narrowed (a warning; an error under `--strict`). A user or library
FUNCTION of the same name keeps its own meaning.

## Standard Function Blocks

Bundled as a compiled `.stlib` library (`libs/iec-standard-fb.stlib`):

| FB | Description |
|----|-------------|
| TON | On-delay timer |
| TOF | Off-delay timer |
| TP | Pulse timer |
| LTON, LTOF, LTP | The timers with an LTIME preset and elapsed time |
| TP_TIME, TON_TIME, TOF_TIME, TP_LTIME, TON_LTIME, TOF_LTIME | The typed timer names of Table 46, on TIME and on LTIME. TP, TON and TOF also take an LTIME preset (`PT`), in a call or assigned (`t.PT := ltimeValue`, also `arr[i].PT` and `s.tm.PT`) |

| CTD | Count-down counter |
| CTUD | Up/down counter |
| R_TRIG | Rising edge detector |
| F_TRIG | Falling edge detector |
| SR | Set-dominant bistable |
| RS | Reset-dominant bistable |

Both counting inputs are sampled on the rising edge, as IEC 61131-3 declares them
(`CU : BOOL R_EDGE`, `CD : BOOL R_EDGE`). A count is registered on the scan where
the input goes FALSE to TRUE, for `CD` exactly as for `CU`.

The counting range follows CODESYS rather than the standard's `PVmin`/`PVmax`:
counting up stops at `PV`, which CODESYS documents as the "upper limit for
incrementing", and counting down stops at 0, which it decrements towards "as long
as `CV` is greater than 0". CODESYS reaches that range by typing `CV` and `PV` as
`WORD`, a deviation from IEC that it documents; these blocks keep the IEC types
and express the same range through the `PV` and 0 guards.

`CTUD` keeps the standard's `IF NOT (CU AND CD)` guard, so simultaneous rising
edges on `CU` and `CD` leave `CV` unchanged. CODESYS does not document that case.

| POINTER TO, `ADR()` | Supported | Full pointer type with dereference; the untyped literal `0` stored in a POINTER TO of any target type or a POINTER TO alias (assignment, initial value, input argument) is NULL, while another integer (a literal, an integer variable or arithmetic of them) passed to a POINTER TO input or initialising a POINTER TO alias is an error, and `p = 0` / `p <> 0` compare the pointer itself, also for a STRUCT target; `p : POINTER TO T := ADR(x);` binds the pointer as an initial value, for a PROGRAM or FB member, a FUNCTION or METHOD local and a global (in a FUNCTION or METHOD `x` must be declared before `p`; a POINTER TO field of a STRUCT takes only NULL or `0` as its default; any other pointer or REF_TO initial value than NULL or `0` is assigned in the body); `p := ADR(x)` takes the address of a variable of any type, a STRUCT, UNION, ARRAY or FB instance included, into a POINTER TO it (`p^.field` reads and writes through it). An ADR bound to a VAR_IN_OUT gets only the binding error. An address that is negated, scaled, combined bitwise or added to another (`-ADR(x)`, `ADR(x) * 2`, `ADR(x) OR 0`, `ADR(x) + ADR(y)`) is refused (`An address can only be offset by + or - an integer`), and so is one as a CASE selector.
